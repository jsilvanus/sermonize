# Implementation plan (v1)

The spec is `README.md` (data model, API, roles). The reasoning is in
`docs/data-model-review.md`. This plan split the API (`packages/api`) into **four sequential
phases**, each small enough for one agent; all four are done. Every phase ended with green checks
and a commit.

## Stack and conventions (all phases)

- Node.js ≥ 22, TypeScript (`strict`), **ESM only** (`"type": "module"`, `NodeNext` modules, `.js` import suffixes).
- Fastify 5 + `@fastify/type-provider-typebox` (TypeBox schemas for every route body, params, querystring and response).
- `pg` (node-postgres) with hand-written SQL. No ORM.
- Migrations: plain numbered SQL files in `packages/api/migrations/` (`0001_*.sql`, …), applied by a tiny runner
  (`packages/api/src/db/migrate.ts`) that records them in a `schema_migrations` table, one transaction per file.
- Tests: `vitest`, running against a real PostgreSQL + pgvector database (`TEST_DATABASE_URL`).
  The test setup drops and recreates the `public` and `private` schemas and runs all migrations.
- Scripts (in `packages/api`): `npm run build` (tsc), `npm run typecheck`, `npm test`, `npm run migrate`,
  `npm run dev` (tsx watch), `npm run cli -- <command>`.
- Config from env: `DATABASE_URL`, `TEST_DATABASE_URL`, `PORT`, `HOST`, `LOG_LEVEL`, `MAX_BATCH_ITEMS` (default 5000).
- Error format: `{ "error": { "code": string, "message": string, "details"?: unknown } }`.
  Codes: `validation_failed` (400/422), `unauthorized` (401), `forbidden` (403), `not_found` (404),
  `conflict` (409), `immutable` (409).
- IDs: UUIDv7 generated by a SQL function `uuid_generate_v7()` (PostgreSQL 16 has no built-in),
  used as the column default.
- Pagination: `?limit=` (default 50, max 500) and `?cursor=` (opaque, base64 of the last id;
  UUIDv7 ids are time-ordered, so keyset pagination on `id` works). Response: `{ items, next_cursor }`.
- Local dev DB in this environment: `postgres://sermonize:sermonize@localhost:5432/sermonize`
  and `…/sermonize_test` (pgvector 0.8.1 installed).

## Phase 1: Foundation, schema, identity and audit

> **Status: done** (commit `e2d81fc`). Deviation: `GET /me` added so scripts can check a token without a role.

Deliverables:
- Project skeleton in `packages/api/`: `package.json`, `tsconfig.json`, `vitest.config.ts`, `src/app.ts` (app factory
  `buildApp({ pool })`), `src/server.ts`, `src/config.ts`, `.env.example`.
- `packages/api/migrations/0001_init.sql` with the **complete** schema from README: extensions (`vector`),
  `uuid_generate_v7()`, `private` schema tables, `app_user`, all scholarly and derived tables,
  `audit_event`, CHECK constraints, FKs `ON DELETE RESTRICT`, indexes on every FK and on filter
  columns (language, year_from/year_to, relation, genre, status).
- Database-enforced rules (triggers/constraints):
  - `created_by`/`created_at`/`updated_by`/`updated_at` filled from `current_setting('app.user_id', true)`.
    Inserts without `app.user_id` fail.
  - `text.body` is immutable (UPDATE of body → error). `CHECK (body IS NFC NORMALIZED)`,
    `CHECK (position(E'\r' in body) = 0)`. `content_sha256` and `char_length` computed by trigger.
  - Derived tables are insert-only (UPDATE/DELETE → error), except `clustering_run.status/completed_at`
    and `withdrawn_*` columns where present.
  - Clusters and memberships can only be inserted while the run is `open`.
  - Embedding dimension equals `embedding_space.dimensions`. Membership embedding belongs to the run's space.
    Cluster belongs to the membership's run.
  - Row-level audit triggers on curated tables (person, work, work_person, sermon_occasion, source, text,
    text_person, app_user, label, label_review, clustering_run status changes, embedding_space, segmentation).
    Changes never include `private` values.
  - `audit_event`: UPDATE/DELETE rejected by trigger.
- `private` functions (`SECURITY DEFINER`, `SET search_path`): `private.resolve_token(token_sha256 text)
  returns table(user_id uuid, role text, kind text)` (ignores revoked/expired tokens and non-active users).
- `packages/api/sql/roles.sql` (ops script, not a migration): creates `sermonize_app` role, revokes `private`
  access, grants EXECUTE on the resolver, INSERT/SELECT on `audit_event` only. Documented in README.
- Auth plugin: parses `Authorization: Bearer <token>`, hashes with SHA-256, resolves principal.
  `request.principal = { userId, role, kind }` or `null`. Helpers `requireRole('contributor')`.
  v1 has no anonymous access: every route except `GET /health` requires at least `reader`.
- DB helper `withTransaction(principal, requestId, fn)`: `BEGIN`, `SET LOCAL app.user_id`,
  `SET LOCAL app.request_id`, run, `COMMIT`/`ROLLBACK`.
- `packages/api/src/lib/batch-audit.ts`: helper to write one `batch_insert` audit event.
- CLI (`packages/api/src/cli.ts`): `migrate`, `create-user --kind human|service --role <role>` (prints user id),
  `create-token --user <id> --name <name>` (prints the token once), `revoke-token <id>`.
  Bootstrap runs with `app.user_id` set to a fixed `system` user created by the migration
  (`00000000-0000-7000-8000-000000000000`, kind `service`, role `admin`).
- Admin routes: `POST /admin/users`, `POST /admin/users/:id/tokens`, `DELETE /admin/tokens/:id`.
  User PII (email, display_name) is accepted in `POST /admin/users` and written to `private.user_pii`
  through a `SECURITY DEFINER` function. It is never returned by any route.
- `GET /health`.
- Tests: migrations apply cleanly; auth (missing/invalid/revoked token → 401, role checks → 403);
  a supplied `created_by` in a body is ignored; body immutability; NFC/`\r` rejection; audit rows written;
  audit_event cannot be updated.

## Phase 2: Scholarly layer API

> **Status: done** (commit `176bc56`). Additions: `POST /works` accepts `persons`/`occasion` and `POST /texts`
> `persons`, so contributors can attribute what they create (the `PUT` endpoints need curator).

Deliverables (`packages/api/src/routes/scholarly/*`):
- persons, works (+ `PUT /works/:id/persons`, `PUT /works/:id/occasion`), sources, texts
  (+ `PUT /texts/:id/persons`), with create, get, list (filters below), PATCH (curator+), withdraw (curator+).
- List filters: persons `?q=` (name ILIKE); works `?genre=&person_id=&year_from=&year_to=&part_of_work_id=`;
  texts `?work_id=&language=&relation=&source_id=`. Withdrawn records hidden unless `?include_withdrawn=true`.
- Texts:
  - `POST /texts` validates NFC and `\n` in the API too (422 with a clear message). The body
    is included in the POST only. Response returns metadata + `content_sha256` + `char_length`.
  - `GET /texts/:id` returns metadata only. `GET /texts/:id/body?start=&end=` returns
    `{ text_id, start, end, content }` using code-point offsets (`substr` in SQL). Restricted bodies need contributor+.
  - PATCH never accepts `body`. `base_text_id` and `supersedes_text_id` must reference existing
    texts of the same work.
  - `translated_from_language` is only allowed when `relation <> 'original'`.
- `sermon_occasion` only allowed for works with genre `sermon`.
- Effective access level for text = most restrictive of text and source.
- Tests: CRUD per entity, filters, pagination, access control for restricted bodies, validation errors,
  multiple originals per work allowed, work with only a translation allowed, PATCH audit rows.

## Phase 3: Segmentations, chunks, embedding spaces, embeddings, search

> **Status: done** (commit `dc7cc2a`). Additions: `GET /texts/:id/segmentations`, `?include_embeddings`/`include_vectors`
> on `GET /chunks/:id`, `hnsw_index` state on spaces, CLI `drop-index`, `date_basis` search filter.
> `GET /chunks/:id/provenance` moved to Phase 4.

Deliverables (`packages/api/src/routes/derived/*`):
- `POST /segmentations` (contributor+, requires `producer`), `GET /segmentations/:id`, `GET /texts/:id/segmentations`.
- `POST /segmentations/:id/chunks`: array of `{ id?, sequence, start_offset, end_offset, text, locus?, language?, metadata? }`
  (≤ `MAX_BATCH_ITEMS`). Server validates each chunk text equals `substr(body, start+1, end-start)`
  and 0 ≤ start < end ≤ char_length. Any failure → 422 listing failing sequences, nothing inserted.
  Idempotent: `ON CONFLICT (segmentation_id, sequence) DO NOTHING`, but a conflicting row with
  different offsets/text → 409. Response `{ inserted, skipped }`. One batch audit event.
  Bulk insert via `unnest` arrays (single statement).
- `GET /segmentations/:id/chunks` (paginated by sequence), `GET /chunks/:id`.
- `POST /embedding-spaces` (contributor+), `GET /embedding-spaces`, `GET /embedding-spaces/:id`.
  Dimensions 1–16000. Name unique.
- `POST /embedding-spaces/:id/embeddings`: array of `{ chunk_id, vector: number[], metadata? }`.
  Validates length = dimensions, finite numbers, chunks exist and aren't withdrawn.
  Idempotent on `(chunk_id, space)` (same response semantics as chunks). One batch audit event.
- `POST /search`: `{ embedding_space_id, vector, limit (≤ 200), filters?: { language?, work_id?, person_id?,
  year_from?, year_to?, relation?, genre?, include_restricted? } }`.
  Uses the space's metric operator (`<=>` cosine, `<#>` inner product, `<->` l2) and casts
  `vector::vector(N)` (N ≤ 2000) or `vector::halfvec(N)` (N > 2000) with `WHERE embedding_space_id = $1`,
  so that the partial index applies. Sets `SET LOCAL hnsw.iterative_scan = relaxed_order` and then
  re-sorts results by distance. Returns chunk, text, work, author summary and distance.
  Restricted chunks are excluded unless the caller is contributor+ and asked for them.
- CLI `create-index <space_id>`: `CREATE INDEX CONCURRENTLY IF NOT EXISTS embedding_hnsw_<short id>
  ON embedding USING hnsw ((vector::vector(N)) <opclass>) WHERE embedding_space_id = '<id>'`
  (halfvec for N > 2000; refuse N > 4000).
- Tests: offset validation with polytonic Greek and an astral-plane character (code points ≠ UTF-16 units),
  idempotent retry, conflict detection, dimension mismatch, search ordering per metric, filters,
  restricted exclusion, index creation + search still correct.

## Phase 4: Clustering, labels, reviews, provenance, API docs

> **Status: done.** Deviations and decisions:
> - `cluster.size` can be filled once while the run is open, completion is checked in the database
>   (≥ 1 membership, sizes match, NULL sizes filled), and `clustering_run.withdrawn_reason` records why a run
>   was withdrawn (like other withdrawals).
> - `cluster.size` counts the memberships of the cluster **and its descendants** (flat clusterings: direct members);
>   `member_count` in responses is the direct count and `GET /clusters/:id/members` lists direct members.
> - Readers see `complete` runs only; open/withdrawn runs and everything under them need contributor+.
>   Labels can only be added to clusters of complete runs; labels of withdrawn runs cannot be reviewed.
> - Restricted chunks in member lists and chunk provenance are returned with `text: null` for readers
>   (metadata stays visible), rather than a 403 for the whole response.
> - Added `GET /clustering-runs/:id/clusters` (runs were otherwise not navigable) and `GET /labels/:id` (with reviews);
>   centroids are returned only with `GET /clusters/:id?include_centroid=true` (contributor+).
> - `/docs` and `/docs/json` are public; the OpenAPI document declares bearer security globally and `security: []`
>   on public routes.

Deliverables:
- `POST /clustering-runs` (contributor+, requires `producer`), `GET /clustering-runs?embedding_space_id=&status=`
  (default status `complete`), `GET /clustering-runs/:id`.
- `POST /clustering-runs/:id/clusters`: array of `{ id?, cluster_number, centroid?, size?, parent_cluster_number?, metadata? }`.
  Idempotent on `(run, cluster_number)`.
- `POST /clustering-runs/:id/memberships`: array of `{ embedding_id, cluster_number | null, distance?, score? }`.
  Validates embedding space and cluster run. Idempotent on `(run, embedding)`.
- `POST /clustering-runs/:id/complete`: open → complete. Computes/verifies `cluster.size` from memberships.
  `POST /clustering-runs/:id/withdraw` (curator+): → withdrawn. Other transitions → 409.
- `GET /clusters/:id`, `GET /clusters/:id/members` (paginated, with chunk summary; restricted rules apply).
- `POST /clusters/:id/labels` (contributor+): `producer_kind = model` requires `model` and `producer`.
  `supersedes_label_id` must belong to the same cluster.
- `GET /clusters/:id/labels`: labels with derived `status` (latest review decision or `proposed`)
  and `superseded` flag.
- `POST /labels/:id/reviews` (curator+).
- `GET /chunks/:id/provenance`: chunk → segmentation (producer) → text → source → work →
  work_person/person → text_person, plus embeddings (space summaries).
- `GET /clusters/:id/provenance`: cluster → run → embedding space, input size, noise count, labels with reviews.
- OpenAPI via `@fastify/swagger` + `@fastify/swagger-ui` at `/docs`.
- `docs/api-examples.md`: curl examples of an end-to-end flow (create work/text, post chunks,
  embeddings, search, cluster run, label, review).
- Tests: full end-to-end flow; frozen run rejects inserts; membership from another space rejected;
  label status derivation; provenance responses complete.

## Definition of done (every phase)

- `npm run typecheck` and `npm test` pass against a fresh test database.
- No PII in any domain table or response; no `user_id` accepted from request bodies.
- README updated if the phase changed anything in the spec.
- One commit per phase, pushed to the working branch.
